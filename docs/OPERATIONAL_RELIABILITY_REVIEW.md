# 运行可靠性审查

审查日期：2026-11-11。范围为每日入口、冻结来源、飞书写入与发布、共享检查点及调度交接；不是全部外部平台和所有故障组合的保证。

## 新发现并修复的问题

| 风险 | 触发场景 | 修复与验证 |
| --- | --- | --- |
| 总数正确但内容错误仍可通过最终回读 | 少一条日数据，换错作品，或两条费用相互抵消 | 按冻结源逐条比对唯一键集合、日指标、采样时间、关联、榜单名次、源行指纹、费用和人数；测试缺行、换ID、数值更改和关联错误 |
| 原生工作流可能偏离程序中的名单 | 手动改了工作流收件人、触发范围或消息字段 | 发布前完整检查实际工作流，包含固定步骤顺序、两类新建待发送触发、准确收件人和正文/标题字段引用；投递前再次检查，异常零写入 |
| 旧的投递异常没有阻止下一批消息 | 上次发送失败、结果未知或仍等待工作流 | 全量通知账本检查；未决发送先对账，禁止新的日报进入工作流，不盲目重发 |
| 未共享的本机缓存被当成完成依据 | 某电脑存在共享HEAD中没有的当日完成标记/冻结快照 | 恢复时保留备份并隔离这类缓存，包括可被提升的临时采集文件；以共享检查点为权威；测试旧完成标记无法继续被复用 |
| 未发布事件证据被两日滚动窗口丢失 | 比较已经完成，但候选由于故障或晚于已发日报而尚未处理 | 根据未消费事件固定保留对应观察对和队列；测试跨越八天仍保留，不自动发送历史队列 |
| 不同电脑时区导致检查错日 | 操作系统时区不是北京时间 | 默认使用Asia/Shanghai的固定UTC+8业务日，入口显式传入运行日，拒绝异日验收收据 |

代码：`operational_validation.py`、`report_publication.py`、`verify_current_base.py`、`daily_reports.py`、`shared_runtime.py`。共享协议v7拒绝旧客户端写入，正常恢复不搬运每天的文件。

## 仍需区分的运行边界

- 代码测试不能验收操作系统调度。必须在实际常开电脑上验证：关闭Codex后触发、账号授权、休眠设置、失败记录和次日真实观察。没有可用执行器，程序无法自行启动。
- 对未知业务写入和异常执行锁保持停止，不用超时抢锁或重试换取表面成功。外部网络/账号不可用仍可能造成漏采，需要具备只读对账与安全恢复能力的执行端。
- `已发送`是原生工作流状态；尚未建立逐个收件人的独立送达/已读验收，不能把状态写成“每人已收到”。
- 部分作品仍缺官方平台ID，部分公开指标没有明确口径；这些是覆盖缺口，不能用总流程成功掩盖，也不能补零或猜配。
- 每日日志和共享历史可能增长，长时间运行需观察耗时与容量。本次不通过删历史证据、降低完整度或扩大通知范围来加速。

## 验证方法

先执行全量模拟测试；在真实Base上只读回读完整来源契约和原生工作流，保留私有证据。检查过程不触发任何通知。协议升级仅写入私有系统运行状态，前后核对通知与业务记录，最后独立核对共享HEAD及锁释放。不能以测试通过声称备用实体电脑无人值守已经验收。
