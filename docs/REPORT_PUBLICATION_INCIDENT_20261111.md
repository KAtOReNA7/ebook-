# 2026-11-11 日报未完整核验即发布

## 发生了什么

当天微信来源已取得完整四榜和作品观察，但同步期间查询执行锁的GitHub只读请求断开。写入保护正确将同步标记为待核，后续依赖模块被阻止；新日报路径却仍把“榜单无法完整核实”和“业务变化缺比较证据”写成正文并投递。

通知不是在采集前运行。它位于来源循环末尾，但此前没有要求所有模块成功：结束、失败、跳过都能走到末尾。因而“最后调用通知”不能替代明确的发布前置条件。源读取故障是触发条件，漏掉发布阻断是错误通知的原因。

## 根因

1. 两条日报替换旧分类汇总时，没有继承旧路径对来源失败的全部阻断。
2. 排行榜与业务正文函数能返回说明缺失的降级文本，调用端将“正文生成成功”当作“信息已经核实”。
3. 通用未知写入检查未覆盖三个来源的同步状态文件。
4. 投递前没有强制执行新鲜、独立的Base完整回读。
5. 既有测试检查了缺失说明文字，却没有断言这种情况下通知写入次数为零。完整来源的测试和此前人工验收未覆盖此次故障组合。

## 修复边界

- 全部来源、费用核对与嵌套业务比较通过后，才执行`report_validation`。新鲜回读需要证明唯一键、关联、费用对账和五榜完整数量及名次。
- 两条日报创建前再检查来源状态、回读日期、四个微信榜版权分布与番茄完整百名版权证据。任一未核实，整批零投递。
- 三个来源的未知同步状态纳入统一保护。不能删guard或盲目重试；既有恢复仍必须先完整只读对账。
- 共享`report_publication_hold`阻止恢复后自动发送；底层收件人校验也拒绝暂停期间发送，包括旧的一次性重发授权。线上同时停用原生工作流。
- 日报是最后的业务发布步骤；投递后仍需要核对通知结果、提交共享检查点并释放锁。
- 网络只读请求的有限重试与上述业务发布检查是独立保护；不能对未知写入重试。

排查还发现：通用“版权有人确认”证据被误当成“磨铁版权确认”，可能生成非磨铁榜单样本的错误上下榜候选。现改为按真实版权值及确认别名判断；已发现的未发送错误候选保留审计并排除，不删除或改写已发送日报。

## 验证与恢复

模拟测试覆盖失败/缺失模块、残榜和版权缺失、嵌套待核比较、未知写入、新鲜回读、显式暂停、同日去重、完整无变化可发两条及错误版权候选排除。测试不发送消息。线上暂停、共享检查点、原生工作流和通知事件均需回读。

公司日报保持暂停；采集可继续。修复通过不等于恢复授权，必须先向负责人说明原因与方案，取得明确恢复指令。恢复前更新参与执行的电脑、核对共享暂停政策与原生工作流；不擅自重发当天日报、旧候选或历史outbox。
