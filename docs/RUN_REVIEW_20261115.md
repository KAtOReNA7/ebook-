## 原因及责任

1. 共享状态读写过重。`Store.read`读取整个状态表再找HEAD；完整发布时，多层`read`/`ensure`再次读取状态数据。每次只读模块复用也进入阶段保存检查，阶段名变化可能导致新增保存工作。阶段增量相对整轮固定基线计算，不等于每步只传本次新增字节。
2. 网络不稳定被串行流程放大。来源读取失败、番茄残榜、飞书TLS超时及GitHub锁查询失败分别触发停止和恢复。全流程重进虽然去重业务写入，却重复支付检查点恢复、模块复核和阶段保存成本。
3. 现场开发混入生产。运行中修复发布门禁后，旧进程仍加载旧代码，需要在发送前停止；临时恢复脚本曾因Windows默认编码读取中文JSON失败。这些均是可避免的额外工作。
4. 采集仍有优化空间。主微信最终598本采样约31分钟，但这不能解释整轮近7小时；应先优化主要状态开销，再有界优化网页并发。

未知写入先对账、完整榜单校验、全局锁和发布前独立核验是必要约束；优化对象是实现方式及重复工作，不能以关闭保护换取速度。
