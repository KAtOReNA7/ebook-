# 任一电脑接续每日任务

**当前版本：v5（2026-11-10正式运行）**。用户已明确接受生产；运行端须更新main，
自动恢复私有runtime中的正式收件名单。v4及更早客户端会拒绝v5，不能降级绕过。
本文下方各日期章节记录当时政策；其中调试期仅owner的说明已由本次批准替代。

2026-11-09起，日常进度不再以某台电脑的本地文件为权威。已配置同一项目、
完成飞书及来源登录、更新到本版本的电脑，都使用原每日入口：

```powershell
python scripts/daily_run.py --run-kind scheduled --dry-run
python scripts/daily_run.py --run-kind scheduled
```

不需要每天导出、复制或导入状态包。首次配置账号与Base访问权限仍需各电脑独立登录；
认证凭据不共享。开发时运行模拟测试或dry-run；直接调用写入脚本没有全局锁会被拒绝。

## 自动接续过程

1. 在既有GitHub仓库的专用协调分支上，通过只允许快进的更新取得全局锁。
   两个竞争者从相同父提交创建不同子提交，只能有一个更新成功。争抢失败的实例停止，
   不写业务数据。该分支只有固定公开说明及随机占用标记，不存业务文件或账号资料。
2. 从现有私有飞书Base的“系统运行状态”表取回最后一个完整共享检查点。
   校验整包和各文件哈希后，自动恢复追踪登记、永久已见ID、费用基线、通知状态、
   当前及前一日快照、来源核验依据。电脑上的原缓存先自动备份。
3. 按原流水线执行。作品起点、30日截止日、日记录唯一键、通知事件键不因换机改变。
   已完成的同日来源复用真实观察，不重新制造“新进入”事件，不回放旧通知。
4. 完成后把状态写回私有飞书，分块回读通过才更新HEAD。使用两个轮换槽，避免
   每日无限新增检查点行；上传中断不会让半个新快照取代完整旧快照。
5. 共享检查点确认后释放锁。每次业务写入还会检查锁归属，不能拿旧授权继续写。

共享状态表是程序辅助表，无需人工编辑。账号Cookie、DPAPI/AES密文、主机配置不上传，
业务状态不进入Git。共享checkpoint保留实际来源字节，迁移后仍可核验官方响应哈希。

## 同日重复、失败与边界

- 同日第二台电脑启动：自动取回第一台电脑的完成状态，已完成模块跳过业务写入。
- 已追踪作品再次出现在列表、连载更新、排序变化：不重建、不重置D0。
- 本地登记与飞书已有追踪日期冲突：在任何作品同步前停止，不让旧日期覆盖已存起点。
- 网络错误、未知写入或进程中断：保留远端锁及回执，不靠超时抢占可能还在写的进程。
  对账可以从共享状态、飞书业务表及回执进行；不能把另一个电脑的目录当作必需权威。
- 旧版程序不认识共享协议，不能与新版混跑。备用电脑必须更新代码一次；更新后不需日常状态搬运。
- 共享锁需要GitHub可达，共享状态需要飞书可达；不可达时停止写入，不能退回各自本地状态。
- “调试中、只通知曹瀚、仅电子书、缺失值不造零、不补历史”的边界不变。

`tools/scheduled_runner.py run --execute`也使用同一共享入口。原来的固定主机角色配置
在共享模式下不再决定谁能运行；是否持有当前全局锁才决定写入权。

## 本次验证

模拟测试覆盖锁竞争、旧持有者失效、上传中断、空缓存恢复、原始字节校验和日期冲突。

## 通知比较与采集分别续接

采集已完成不代表通知比较已完成。每日入口另存`notification-comparison.json`：
缺前日证据为`waiting_evidence`，补齐后比较为`compared`；来源原来已完成比较则不重放。
该进度、前后两日冻结快照、事件队列、已消费事件ID和补发写入保护均进入共享检查点。
尚未完成比较的日期会保留证据，不因滚动到第三天而丢失。另一台电脑补齐真实来源后，
持锁执行入口会自动将证据加入共享状态；以后的正常换机无需人工传递文件。

同日每日入口在统一汇总前自动续做此前缺证据的比较，仍按既有事件ID去重。
跨日不自动回放；必须在私有`config/notification-recovery.json`中记录用户明确授权的日期。
已授权日期使用以下入口（先dry-run，然后执行）：

```powershell
python scripts/resume_daily_notifications.py --date YYYY-MM-DD --dry-run
python scripts/resume_daily_notifications.py --date YYYY-MM-DD
```

它同样取得全局锁、自动恢复和提交共享检查点，只重算相邻真实采样产生的未发送通知，
不重新采集、不修改日数据和追踪起点、不读取旧outbox补发。两个来源的比较证据必须齐全；
微信四榜各50名、番茄100名验证通过。未开分等单项指标缺失仍留待核，不伪造数值。
同类已发送且出现额外成员时停止核查，不再发第二条同类消息。补发正文标记真实补发时刻。
dry-run证据指纹必须与写入时一致，账号仍仅owner；未知写入先完整对账，不能盲重试。

## 2026-11-09 日报格式替换

私有`daily-notification-format.json`的`mode=two_daily_reports`替代旧分类消息。
业务事件继续采集与去重，发送时整合进一条《年月日电子书明细》，同时发送一条
《年月日微信读书汇总》。四榜分别按版权方上榜本数做竞争排名（相同数量并列，
后续跳位）；磨铁零上榜不参与排名；缺版权明确披露，缺榜不能当零。
授权的历史比较补发也使用新电子书明细格式，不另发旧类别消息。
每日报告上下文、发送保护与格式配置进入共享检查点；已发送同日报告不得覆盖或重发。
日报后的新增事件仍保留待核，不重复发送。测试使用独立去重键，只有用户明确授权才运行。
`weread-copyright-confirmations.json`保存按官方ID、书名、作者核实的版权补充及来源，
平台原文字段保留为空；有新平台版权时以平台字段为准，不将出版社当作版权方。

## 跨机审计补强：检查点v2

新客户端可读v1和v2，提交时统一v2。旧v1客户端的schema校验会在进入业务阶段前
拒绝v2，不会把不认识的新政策静默丢弃；需先安全升级代码。未采用共享协议的更早
程序无法由检查点约束，必须保持停用。后续有不兼容共享政策时应提升协议版本。

版权方上新业务配置从publisher-newbooks.json分离生成publisher-business.json，
随私有检查点共享；目标本机session_file保留，登录文件不复制。上新原始证据包含
子目录，按原字节校验。手工新增通知和费用通知的未完成写入保护也纳入全局检查。

任一电脑可执行 `python tools/check_shared_runner.py --online` 只读检查依赖、锁与
远端检查点。它不获取锁、不恢复缓存、不写Base、不发送通知，只在本地存GET收据。
源会话有效性、Windows账户和10点调度仍需真实dry-run/任务触发验收；不能以文件
存在或模拟测试通过替代。Windows部署按WINDOWS_RUNNER_HANDOFF.md执行。

## 2026-11-10 日报精简与指定重发（v3）

本次修订引入v3，新客户端仍能读取v1/v2；旧客户端拒绝v3，须更新后再执行，
避免另一台电脑继续使用旧日报格式。电子书明细只保留营销变化及业务变化，
不列日期、采集同步摘要和待核实章节；营销无新增/变更时显示“无”，源未核实时
不得误报“无”。营销明细沿用已有营销汇总的逐条内容。微信汇总删除开头说明和
采样时刻正文（原始证据仍保留），零磨铁榜单按本数排序只列前五家，保持并列名次；
同本数以名称稳定排序，避免并列导致展示数量无限增加。

用户明确指定的单次重发通过authorized-report-resends.json按事件唯一键、日期、
全部内容与收件人哈希严格限权；已完成授权关闭，不影响日常owner_only设置。
原生工作流临时限制到指定重发事件和收件人，回读发送状态后恢复原定义。
任何未知写入或未完成工作流恢复由report-resend.apply-state.json阻止日常继续。
重发事件使用独立键，不能覆盖已发送日报，也不能因程序复跑再次发送。
