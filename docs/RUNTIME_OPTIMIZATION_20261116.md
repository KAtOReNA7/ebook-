# 每日任务效率优化：2026-11-16

本轮以 `8df98a9` 为基准，完成代码修改和离线模拟。没有执行生产日任务、重跑11月15日、发送测试或日报。真实60分钟总耗时／来源齐备后15分钟目标**尚未验收**。

## 实际改动

- 共享HEAD改为精确键查询；完整内容读取限定槽位，HEAD提交前后仍校验全部有效块与整体哈希。读后再次读取HEAD，拒绝混合代次。写槽位和写HEAD的ensure不再各扫全表。
- 阶段HEAD单独读取；相同内容也保留完整核验。一个已确认完成的阶段之后，如果共享内容逐字节不变，只读模块结束不再因阶段名称不同重新上传。写前、失败、内容变化、未确认保存均不跳过。
- 保留v8、双槽和全部历史证据；未引入新服务、状态迁移、锁缓存或自动抢锁。
- 微信与番茄单个GET最多三次，只有瞬时网络错误及指定临时HTTP状态重试。成功请求不重采；403、业务解析和身份错误不靠重试掩盖。微信今日阅读搜索采用两个并发任务，与已有详情并发上限一致。
- 飞书CLI仅无payload的白名单只读命令允许最多三次瞬时网络重试，保留分次回执；失败的NDJSON另存，不让重试覆盖失败证据。写入一次失败仍保留PENDING并停止，必须对账。
- 微信今日阅读请求报错与平台确实缺字段分开：前者阻断两条日报；未开分或成功响应中缺明确指标仍为空。版权方追踪中的指标请求错误同样计入失败。
- 增加 `--fanqie-ranking-source <snapshot.json>`：仅显式复用当日、完整100名、官方原文哈希与重算结果一致的观察。保留原采样时间；不替换已冻结观察，不接受旧日期。原有共享入口、写前留证、五榜检查和发布门禁仍执行。
- 番茄详情每次采集使用独立尝试目录，保留中断证据；只有日期及成功/失败ID全集与请求相符的完整结果账本才冻结。共享检查点保留尝试目录原始JSON。采集进程报错仍向上报告，不能因存在快照而认定成功。
- CLI增加逐次耗时回执；阶段输出开始和完成耗时，私有阶段context记录capture及保存耗时。方便下一次真实运行直接定位瓶颈。

| 路径 | 调用数：旧→新 | 返回字节MB：旧→新 | 本机离线墙钟秒：旧→新 |

## 验证与剩余瓶颈

全量 `python -m unittest discover -s tests -q`：424项，415通过、9项跳过。模拟测试覆盖：完整分页、双槽失败不推进HEAD、损坏块及变化HEAD拒绝、未知写入不重试、错租约拒绝、跨机原字节恢复、日报去重、发布失败零投递、网络读重试上限、指标请求失败停发、无变化阶段零远端调用、榜单复用日期及证据检查。跳过项不计为通过，模拟不代表真实平台验收。

仍未解决：

1. 阶段增量仍相对于本轮固定基线。变化阶段仍可能重传较大压缩包，历史保留证据未裁剪；后续需按引用关系评估归档或内容寻址，不能直接删除。
2. 文本contains槽位筛选可能同时返回同后缀的阶段槽以及过去更长槽的尾部。代码仅组装HEAD指定的块，完整哈希核验；目前只是缩小范围，尚非最少块查询。
3. 泛化故障接续、已同步冻结微信指标的受控定点补采仍须补齐；本轮没有假称做到任意失败全自动续跑。共享最终提交的现有“只恢复提交”能力保持不变。
4. 独立发布前全量Base回读、锁归属和实际收件人检查保留；这部分耗时没有通过缓存规避。
5. Windows自动触发错误仍是独立调度问题，本轮开发不构成周末触发验收。
